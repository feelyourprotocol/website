# x402 & Agent Payments

x402 is an open payment protocol built into the request itself. For us, it is the likely rail for agents buying EIPs that are still ahead of the open hardfork.

It is not part of the [open server](/roadmap/launch). The hosted MCP is free. Payment follows after we have usage, a stable service, and something new to sell.

<Motto>The protocol can pay today. The agent experience is still being assembled.</Motto>

## What x402 is now

HTTP already had a status for payment: **402 Payment Required**. x402 defines the request, payment proof, verification, settlement, and retry around it. A facilitator can verify and settle onchain without the seller running payment infrastructure.

## Why it fits this product

| Property | Fit | Question still open |
| --- | --- | --- |
| Pay per call | A fixed USDC amount per tool, known before the run | Whether two and four cents hold once people use it |
| No account required | Agents can buy one capability without a SaaS signup | What receipt and support path replaces an account history? |
| Stablecoins | Our early users already understand wallets and Base | How much wallet setup will they tolerate? |
| Machine-readable quote | The buyer can decide before EthereumJS runs | Which facts must every quote expose? |
| Open ecosystem | Wallets, facilitators, and sellers can evolve separately | Which providers are reliable enough for production? |

The product remains the deterministic run. x402 is the access rail. [Pricing](/monetization/pricing#access-cycle) owns the free-to-paid cycle; [token utility](/monetization/token) owns any later holder discount.

## The integration gap

x402 V2 already has MCP wrappers, buyer spend controls, lifecycle hooks, discovery through Bazaar, and signed offers and receipts. Coinbase ships a separate Agentic Wallet MCP with funding and human-set limits. Open-source wallet MCPs can also be added to Cursor and Claude.

What does **not** exist yet is one native wallet contract shared by Cursor, Claude, and every other harness.

| Layer | State | Consequence for us |
| --- | --- | --- |
| Seller protocol | Usable now | We can build standards-first on x402 V2 |
| Settlement | Hosted facilitators exist | Keep the facilitator replaceable |
| Wallet | Working companion MCPs exist | Document paths; do not build custody |
| Harness | Wallets are add-ons, not a native universal slot | Expect setup, funding, and policy friction |
| MCP authorization | OAuth protects access; it does not provide payment | Keep authentication and payment separate |
| Autonomous policy | Spend caps and hooks exist in code | Never rely on a model prompt to protect funds |

<IconNote icon="shield" title="Strategy: merchant-ready, wallet-agnostic">

Build the seller side once. Test against more than one buyer. Publish a known-good bridge for Cursor and Claude, while keeping payment logic out of the model and out of our engine.

</IconNote>

<IconNote icon="boundary" title="What we do not build">

No first-party wallet, custody, onramp, or facilitator. Those layers move faster than the simulation service and carry a different security burden.

</IconNote>

**Integration references:** [x402 with MCP](https://docs.x402.org/guides/mcp-server-with-x402), [buyer spend controls](https://docs.x402.org/getting-started/quickstart-for-buyers), [Coinbase Agentic Wallet MCP](https://docs.cdp.coinbase.com/agentic-wallet/mcp/welcome), [MCP authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization).

The message is not “pay because x402 is exciting.” It is: **get useful early protocol access, and help make agent-native payment real.**

What we can offer:

- a small paid beta around frame transactions and the EIPs after it;
- an explicit compatibility matrix for wallets, harnesses, and facilitators;
- short, public reports on setup time, failed payments, retries, and receipts;
- direct feedback into quote semantics and buyer policy.

## Agent-to-agent horizon

The goal is a buyer agent that can discover the service, judge the offer, pay within policy, run the tool, and verify what came back—without a person reading this site.

### Decide before the paid beta

| Decision | Plausible path |
| --- | --- |
| Charge shape | Fixed price per tool ([Pricing](/monetization/pricing#the-price)). Exact quotes, not metered gas |
| Buyer policy | Amount, asset, network, seller, tool, per-call and session ceilings |
| Failure | Define expired quote, rejected signature, settlement timeout, engine error, and retry |
| Delivery proof | Signed offers and receipts, plus the existing run provenance |
| Discounts | Apply outside the engine; never make the community token a prerequisite |
| Discovery | Bazaar first for x402; MCP registry later for general discovery |

## Three to five months

Likely: more wallet MCPs, more Bazaar-listed tools, stronger spend policy, and better receipts. Possible: harnesses expose wallet UX more directly. Uncertain: one wallet interface becomes standard across them.

Our position should work in all three cases:

1. **Seller-ready.** A conforming x402 buyer can pay us.
2. **Client-agnostic.** No dependency on one wallet or harness.
3. **Safe by construction.** Buyer policy lives in code; retries cannot double-charge.
4. **Discoverable.** Metadata is ready when registry work moves from Later.
5. **Observable.** We can see quote → payment → execution → receipt without storing agent secrets.

The first milestone is not “fully autonomous commerce.” It is one external agent, using a bounded wallet, discovering and buying one useful run end to end.
